Everest Textile Mills: one system from yarn to profit

WeaveSphere replaces notebooks and phone calls at a textile mill. Yarn arrives, gets issued to orders, becomes fabric on machines, is cut into QR-coded rolls, passes quality control, ships on a truck with an invoice, and lands in the month-end P&L. Every roll is traceable back to its order, machine, shift, operator, yarn and QC history.

Guiding principle from the spec: code for rules, Jev for decisions, an LLM for words. Nothing involving stock, money or dispatch is ever decided by AI.

2. System architecture

Three parts: a plain-JavaScript frontend served by Vite, a single FastAPI backend over SQLite, and OpenRouter for all AI. The buyer's tracking page is the only thing that works without signing in.

3. Life of a request

Example: the store keeper issues 200 kg of yarn to an order.

POST /api/issues→Vite proxy→user() verifies the JWT, checks it isn't revoked, re-reads the role→role("admin","store"); owner always passes→pydantic checks qty_kg > 0→get_db(): fresh connection→tx(): BEGIN IMMEDIATE→read stock + moving-avg rate→enough? insert issue with rate : 409→COMMIT→return issue + low-stock list

Connections and threads

Every endpoint is a plain def, so FastAPI runs it in a worker thread, never on the event loop. Each request gets its own SQLite connection (busy_timeout 5 s) and closes it at the end.

Transactions

Connections run in autocommit. Anything that reads and then writes based on what it read (stock, dispatch scans, QC, review resolution) is wrapped in tx(), which takes SQLite's write lock up front with BEGIN IMMEDIATE.

Errors

  • Business rule blocked → 409 with a readable message
  • Bad input → 422, always one line of text
  • Duplicate / missing reference → 409 "Already exists…" / "refers to a record that does not exist"
  • AI down → 503 on text features only

AI calls never hold locks

The write is committed first; the Jev call happens afterwards. A slow AI call delays only that one response, never another user's write.

25 STRICT tables, one computed view. The core idea of the spec: every roll links to order → machine → shift → operator → QC → dispatch.

6. Hard guarantees (code, never AI)

Stock can't go negative

The issue endpoint takes the database write lock before reading stock. Two simultaneous issues of the last 100 kg: one succeeds, the other gets 409 only 0 kg in stock. Proven by a two-thread test.

A roll ships once

dispatch_items.roll_id is UNIQUE in the database. The scan also checks: truck still open, roll belongs to this order, roll is QC-passed. Each block returns a BLOCKED: … message.

Invoices are arithmetic

Metres scanned × order price, GST from the fabric type, rounded to paise and stored at close. Created in the same transaction that marks rolls dispatched.

QC can't be decided twice

A roll must be pending_qc or rework; otherwise 409. Rework and reject require a defect type or notes.

Database-level rules

STRICT typing, CHECK constraints on every enum and quantity, foreign keys on, UNIQUE where duplicates would be wrong (machine names, yarn types, BOM lines, tracking tokens, roll codes).

Payments match invoices

A buyer payment linked to an invoice must come from that invoice's buyer.

Everything goes through OpenRouter with one key. mill/ai.py is the only file that knows about models.

Words (chat model)

  • Reply draft in English, Tamil or Hindi from live order data only; a person edits and marks it sent.
  • Challan photo → suggested GRN fields; the store keeper confirms before saving.

Never AI

  • Stock levels, issue limits
  • Dispatch guards, invoices, GST
  • Wages, cost per order, P&L
  • Machine status itself (set by a person)

Failure mode

Any error, timeout (5 s) or out-of-range answer gives confidence 0, so the decision goes to the review queue. Nothing blocks the floor. Text features return 503 and the person writes it by hand.

Learning the threshold

Every decision is logged in ai_reviews, including automatic ones, and any can be corrected. /reviews/accuracy shows how often Jev matched the person per confidence band. Default threshold 0.8; 0.7 used for the demo.

12. Interview Q&A

Click a question to see the answer. Each answer points to evidence you can show.

Why no ORM? How do you prevent SQL injection?

Every value is a bound parameter. Table and column names are only built into SQL in a few places, and each comes from code or is checked against the real schema via PRAGMA table_info (master data) or a fixed field list (AI decisions).

Rules live in the database itself (STRICT types, CHECK, UNIQUE, foreign keys), so they hold no matter what code writes. For a growing team I'd add SQLAlchemy Core for query building, not a full ORM.

Stock is recalculated on every read. What happens at 2 million rows?

Measured: 500k GRNs and 2M issues. Without indexes, the full stock page took 4.2 s. With two covering indexes on (yarn_type_id, qty_kg, rate) it takes 79 ms, and the per-issue check takes 1 ms.

Beyond that I'd snapshot balances per closed month and sum only from the last snapshot, which keeps the no-drift property.

Two people issue the last 100 kg at the same moment. What happens?

BEGIN IMMEDIATE takes SQLite's write lock before the stock read. The second request waits (up to 5 s), then reads 0 kg and gets a 409. The lock is file-level, so it holds across server processes too.

Evidence: a two-thread test with a slowed stock read; exactly one wins every round, and it fails when the lock is removed. Also: supervisors can't issue yarn at all; only store, admin, owner.

How did you pick the confidence threshold? What if the AI is confidently wrong?

Honestly: from two live runs, not calibration. That's why every decision is now logged and correctable, and /reviews/accuracy reports agreement per confidence band. The threshold should be set from that data.

Blast radius is bounded by design: AI only sets labels and routing. Machine status, stock, money and dispatch are set by people or code. Who to send to a breakdown is a rule from the category. A wrong label is corrected in one call, which re-applies the fields (including the assignee).

Jev takes 0.6–2.9 s. Doesn't that block FastAPI?

No. Endpoints are plain def, so FastAPI runs them in its thread pool; the event loop stays free. The database write is committed before the AI call, so no lock is held while waiting. Only the person who submitted waits; the call times out at 5 s and falls back to the review queue.

If floor staff find the wait disruptive, move the AI call to a background task and show the result when it arrives.

Average costing distorts P&L when prices swing. How hard is FIFO?

The original version had a worse problem than the question: it averaged over every GRN ever, so a new delivery rewrote past months. Fixed: each issue saves the moving-average rate of stock on hand at that moment, and reports use the saved rate. Moving average is an accepted method under Ind AS 2.

For FIFO: each GRN already works as a batch with its own rate. Add one table linking each issue to the GRNs it consumed, allocate inside the same issue lock, and change two cost queries. About 40 lines. Out of scope in the spec.

Five orders need the same yarn. Does feasibility tell all five "can start"?

Not any more. Each order subtracts what earlier open orders still need (requirement minus already issued) before comparing with stock. Every yarn line shows reserved_kg and free_kg. Priority is first come, first served by order number.

Next steps if needed: a priority column, then a hard-allocation table checked by the issue endpoint.

Why SQLite for a production system?

One mill, a few dozen users, writes measured in hundreds per day. SQLite in WAL mode gives concurrent readers, a single serialised writer, real transactions and constraints, with no server to run. Backups are one file (taken safely with SQLite's .backup command). Moving to Postgres means a new connection layer plus porting a handful of SQLite-specific bits: STRICT tables, date('now')/strftime, two-argument MAX() and INSERT OR IGNORE. The queries themselves are standard SQL.

What happens when OpenRouter is down?

Nothing stops. Every Jev decision gets confidence 0 and lands in the review queue with empty fields; the risk flag shows "unknown"; reply drafting and challan reading return 503 and people type it themselves. All rules, stock, dispatch and money keep working because none of them touch AI.

How is the buyer tracking link secured?

Each order gets a 128-bit random token (secrets.token_urlsafe(16)). The public endpoint returns only progress, stage, ETA and dispatch summary for that one order: no prices, no other orders. Gap: tokens can't be revoked yet; adding a "regenerate link" endpoint is a one-liner.

How do you know the whole thing works?

One end-to-end test drives the full demo over HTTP, from GRN to P&L, with exact expected figures. A dedicated race test proves the stock lock. A live smoke script hits the real AI with the app's exact questions. And the frontend was clicked through screen by screen against a seeded database.

What would you do with another month?

Password reset and user deactivation; WhatsApp integration for real message intake and sending; a camera QR scanner on phones; calibrate the AI threshold from the accuracy report; per-month stock snapshots.
